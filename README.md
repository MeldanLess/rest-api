# ApplyTrack API

[![CI](https://github.com/MeldanLess/rest-api/actions/workflows/ci.yml/badge.svg)](https://github.com/MeldanLess/rest-api/actions/workflows/ci.yml)
![Python 3.12](https://img.shields.io/badge/python-3.12-4338ca.svg)
![FastAPI](https://img.shields.io/badge/FastAPI-0.115-009688.svg)
![License: MIT](https://img.shields.io/badge/License-MIT-0f7b4f.svg)

**Боевой API:** https://api.example.com/docs · **Исходники:** https://github.com/MeldanLess/rest-api

REST API для учёта откликов на вакансии, сделанный по образцу production-сервиса
на FastAPI, PostgreSQL и Docker. Он существует, чтобы решить мою собственную
задачу с поиском работы — но интересна здесь не предметная область, а то, что
API ведёт себя как то, что команда действительно развернула бы: миграции,
контейнеризация, тесты против настоящей базы и записанные компромиссы.

---

## Задача

Учёт откликов в таблице ломается предсказуемым образом. Нельзя отфильтровать
по этапу, не пересортировав столбцы; нельзя ответить на вопрос «сколько обычно
жду первого ответа»; и не видно формы собственной воронки — куда я откликаюсь,
что работает, а что нет.

Этот API чинит все три вещи. Он ведёт **неизменяемую историю** каждой смены
этапа — именно она делает возможными таймлайн и статистику по времени ответа —
и отдаёт воронку данными, а не строками в таблице.

**Почему именно эта область:** это настоящий инструмент, которым я
пользуюсь, поэтому решения ниже — те, с которыми мне пришлось жить, а не те,
которые можно было пропустить.

## Что он умеет

| Эндпоинт | Назначение |
|---|---|
| `POST /auth/register` | Создать аккаунт |
| `POST /auth/token` | Войти и получить JWT (поток OAuth2 с паролем) |
| `GET /auth/me` | Текущий пользователь |
| `GET /applications` | Список, фильтры, поиск и постраничный вывод |
| `POST /applications` | Создать отклик |
| `GET /applications/{id}` | Прочитать один |
| `PATCH /applications/{id}` | Частичное обновление |
| `DELETE /applications/{id}` | Удалить |
| `POST /applications/{id}/stage` | Сменить этап — событие попадёт в историю |
| `GET /applications/{id}/events` | Полная история |
| `GET /stats/pipeline` | Счётчики по этапам и источникам, доля офферов, медианное время ответа |
| `GET /health` | Живость приложения и готовность базы |

**Правила предметной области, которые обеспечивает API:**

- Переход между этапами, не имеющий смысла, отклоняется кодом **409**.
  `applied → offer` перепрыгивает скрининг и собеседование, поэтому такой
  переход запрещён. Движение *назад* разрешено — компания может перенести
  собеседование, а инструмент, отказывающийся записывать реальность, хуже,
  чем никакого инструмента.
- Этап нельзя изменить через `PATCH`. У него есть собственный эндпоинт, так
  что каждое изменение попадает в историю. Изменить прошлое нельзя.
- Отклик другого пользователя возвращает **404, а не 403** — 403 подтвердил бы,
  что такой id существует.
- Неудачный вход возвращает одно и то же сообщение и для неизвестной почты,
  и для неверного пароля, поэтому по эндпоинту нельзя выяснить, кто
  зарегистрирован.
- Каждый ответ несёт заголовок `X-Request-ID`, и в теле каждой ошибки лежит
  тот же id — благодаря этому сообщение об ошибке можно сопоставить со строкой
  в логе.

## Стек

| Слой | Выбор | Почему |
|---|---|---|
| Фреймворк | FastAPI 0.115 | Тела запросов, проверенные типами, и схема OpenAPI, генерируемая из кода, — документация не может разойтись с реализацией |
| Валидация данных | Pydantic v2 | Один слой схем, который и проверяет вход, и сериализует выход |
| ORM | SQLAlchemy 2.0 | Типизированные модели `Mapped[...]`; стиль 2.0 — нынешний общепринятый |
| Миграции | Alembic | История схемы — источник истины, а не `create_all` |
| База данных | PostgreSQL 16 | Настоящие типы enum, колонки UUID, `ILIKE`, даты с часовым поясом |
| Аутентификация | PyJWT + bcrypt | Стандартные bearer-токены JWT; bcrypt со своей солью на каждый пароль |
| Логирование | стандартная библиотека `logging` | Идентификатор запроса в каждой строке, JSON в бою — без сторонних зависимостей |
| Тесты | pytest + httpx | Идут против настоящего экземпляра PostgreSQL, а не против SQLite |
| Статический анализ | Ruff | Быстро, и один инструмент вместо flake8 + isort + black |
| Контейнеры | Docker + Compose | Тот же образ работает локально, в CI и в бою |

## Быстрый старт

### С Docker (рекомендуемый путь)

```bash
git clone https://github.com/MeldanLess/rest-api.git
cd rest-api
docker compose up --build
```

Дальше откройте <http://localhost:8000/docs>.

Compose поднимает PostgreSQL, дожидается его готовности, накатывает миграции
и запускает API с горячей перезагрузкой. Больше ничего ставить не нужно.

### Без Docker

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt

cp .env.example .env             # поправьте DATABASE_URL
docker compose up -d db          # либо укажите в DATABASE_URL свой Postgres

alembic upgrade head
uvicorn app.main:app --reload
```

### Наполнить демо-данными

```bash
python -m app.seed
```

Создаёт `demo@example.com` / `demo12345` и восемь правдоподобных откликов,
распределённых по всем этапам, чтобы эндпоинту со статистикой было что показать.

### Развернуть

API работает на обычном Linux-сервере: Docker для API и PostgreSQL, nginx
перед ним для TLS, systemd управляет жизненным циклом. Тот же образ работает
локально, в CI и в бою.

```bash
git clone https://github.com/MeldanLess/rest-api.git /opt/applytrack
cd /opt/applytrack
cp deploy/env.production.example deploy/env.production   # дальше заполнить
sudo cp deploy/applytrack.service /etc/systemd/system/
sudo systemctl enable --now applytrack
```

Полный разбор — DNS, TLS, миграции, ночные бэкапы, релизы и откат — в
**[docs/DEPLOYMENT.md](docs/DEPLOYMENT.md)**.

## Как запустить тесты

```bash
# 1. поднять базу
docker compose up -d db

# 2. поставить зависимости для разработки
pip install -r requirements-dev.txt

# 3. прогнать набор
pytest -v
pytest --cov=app --cov-report=term-missing
```

Набор создаёт **отдельную** базу `applytrack_test`, накатывает на неё миграции
Alembic и очищает каждую таблицу между тестами. Вашу базу для разработки он
не трогает.

**73 теста, покрытие 87%** (с учётом ветвлений) — цифры из отчёта CI, а не
оценка на глаз.

Почему настоящий PostgreSQL, а не SQLite: SQLite стартует за миллисекунды, но
он же тихо меняет поведение ровно тех вещей, ради которых этот проект и
существует, — нативных типов enum, колонок UUID, поиска через `ILIKE` и дат с
часовым поясом. Набор тестов, который проходит на SQLite и падает на
PostgreSQL, хуже, чем никакого набора тестов.

В CI то же самое делает сервис-контейнер PostgreSQL, поэтому тесты, которые
проходят локально, проходят и на GitHub.

## Проектные решения и компромиссы

**Синхронный SQLAlchemy, а не async.** Очевидный «современный» выбор — эндпоинты
`async def` с `asyncpg`. Я выбрал синхронный SQLAlchemy с `psycopg`, потому что
нагрузка — это несколько сотен строк для одного пользователя, и на таком
масштабе корректность важнее пропускной способности. FastAPI выполняет
синхронные эндпоинты в пуле потоков, так что цикл событий не блокируется.
Компромисс настоящий: если бы сервис обслуживал тысячи параллельных
писателей, я перешёл бы на async — и README об этом написал бы.

**Отдельная таблица истории вместо изменяемого столбца `stage`.** Альтернатива —
хранить только текущий этап и перезаписывать его. Теряется всё интересное:
нельзя посчитать «дни до первого ответа» или «дни до оффера» и не видно, что до
ответа было шесть собеседований. Таблица истории стоит одного лишнего INSERT на
каждую смену этапа и даёт весь эндпоинт со статистикой.

**`clock_timestamp()` вместо `now()`.** `now()` в PostgreSQL возвращает время
*транзакции*, поэтому две строки, записанные в одной транзакции, получат
одинаковое значение — а сортировка журнала аудита по столбцу с ничьими это
гарантированный баг. `clock_timestamp()` возвращает фактическое время выполнения
оператора, поэтому последовательные вставки различаются. Порядок событий
дополнительно разводится по `id`, так что порядок получается полным.

**Напрямую bcrypt, а не `passlib`.** `passlib` не поддерживается с 2020 года, и
его бэкенд для bcrypt ломается на bcrypt 4.x. Вызовы `bcrypt.hashpw` и
`bcrypt.checkpw` — это две строки и на одну зависимость меньше. Плата за это —
ограничение bcrypt в 72 байта пришлось обрабатывать самому, поэтому схема
ограничивает длину, а API отклоняет слишком длинный пароль понятным 422, а не
падает молча в момент хеширования.

**Значения enum в базе, а не имена enum.** По умолчанию SQLAlchemy сохраняет
`Stage.APPLIED` как `"APPLIED"`, а API говорит строчными — `"applied"`. Одно
написание везде стоит небольшого помощника `values_callable`, потому что база,
которая не согласна с API в том, как называется этап, — это баг, который
всплывает только в запросе.

**404, а не 403, для чужой строки.** Ответ 403 говорит «такой id существует,
но не для вас» — это оракул существования. Каждый отклик фильтруется по
владельцу прямо в запросе, поэтому строка просто не находится.

**Статистика считается на Python, а не одним большим SQL-запросом.** Набор
данных — это отклики одного человека на работу. Читаемый Python здесь стоит
больше, чем сэкономленные миллисекунды на запросе, который и так мгновенный, а
логику агрегации можно тестировать отдельно.

**У ошибок одна форма.** Каждый ответ с ошибкой — валидация, 404, 409 — имеет
одно и то же тело: `detail`, `status_code`, `path` и `request_id`. Клиент пишет
один обработчик ошибок вместо четырёх, а пользователь, сообщающий о проблеме,
может назвать `request_id`, который совпадает со строкой в логе.

## Логирование

Каждая строка лога несёт **идентификатор запроса**, и каждый ответ — тоже: в
заголовке `X-Request-ID` и в теле каждой ошибки.

```
2026-11-09 14:22:31 INFO    [9f2c1a8e4b7d] app.routers.auth: вход выполнен user_id=…
2026-11-09 14:22:31 INFO    [9f2c1a8e4b7d] app: запрос завершён event=request.completed method=GET path=/applications status_code=200 duration_ms=4.12
```

В бою формат переключается на один объект JSON на строку — именно такой формат
умеет индексировать сборщик логов:

```json
{"timestamp":"2026-11-09T14:22:31+0000","level":"INFO","logger":"app","message":"запрос завершён","request_id":"9f2c1a8e4b7d","method":"GET","path":"/applications","status_code":200,"duration_ms":4.12}
```

| Настройка | По умолчанию | Значение |
|---|---|---|
| `LOG_LEVEL` | `INFO` | Уровень корневого логгера |
| `LOG_FORMAT` | `console` | `console` или `json`; при `ENVIRONMENT=production` по умолчанию `json` |

Четыре решения стоит назвать отдельно:

- **Идентификатор запроса — это `ContextVar`, а не thread-local.** FastAPI
  выполняет синхронные эндпоинты в пуле потоков, и thread-local был бы
  не виден тому обработчику, которому он нужен.
- **Переданный вызывающей стороной `X-Request-ID` учитывается, но только после
  проверки.** Значение возвращается в заголовке ответа и попадает в строку
  лога, поэтому id, содержащий что-то кроме `[A-Za-z0-9_-]{1,64}`, заменяется
  сгенерированным, а не пропускается как есть.
- **Учётные данные не попадают в лог.** Неудачный вход записывается с
  усечённым SHA-256 от адреса почты вместо самого адреса — этого достаточно,
  чтобы заметить перебор по одному аккаунту, не записав персональные данные в
  файл, который многие могут прочитать.
- **Middleware написан на сыром ASGI, а не на `BaseHTTPMiddleware`.** Последний
  оборачивает ответ в новый `StreamingResponse`, из-за чего ломаются фоновые
  задачи. Middleware достаточно мал, чтобы платить за это не было причин.

## Что я доделал бы, если будет время

- **Ограничение частоты запросов** на `/auth/token`. bcrypt намеренно медленный,
  а для хеширования паролей это правильное свойство и неправильное для
  эндпоинта входа под атакой. Ограничитель slowapi решил бы задачу.
- **Refresh-токены.** Сейчас токен живёт 24 часа, и его нельзя отозвать.
  Правильной формой был бы короткоживущий access-токен плюс ротируемый
  refresh-токен, хранимый в хешированном виде.
- **`PUT` для ресурса отклика** — клиентам, которые хотят прислать объект
  целиком, а не частичное обновление.
- **Постраничный вывод по курсору.** `LIMIT`/`OFFSET` деградирует на больших
  таблицах, потому что база всё равно должна пропустить отбрасываемые строки.
  Постраничный вывод по ключу `(created_at, id)` — не деградирует.
- **Описание OpenAPI для каждого ответа с ошибкой**, чтобы сгенерированные типы
  клиента описывали и сценарии отказа.
- **Метрики.** Логи говорят, насколько медленным был запрос, но не говорят,
  сколько запросов было и каков процент ошибок. Клиент Prometheus и эндпоинт
  `/metrics` сделали бы API наблюдаемым без чтения логов.
- **Отправка логов.** API пишет структурированные логи, но пока никуда их не
  отправляет. Не хватает обработчика, пишущего JSON-строки в подключённый том,
  либо `logging.handlers.SysLogHandler`.

ruff check .              # проверка стиля

alembic revision --autogenerate -m "добавить x"   # новая миграция
